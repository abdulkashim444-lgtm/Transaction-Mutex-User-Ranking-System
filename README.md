# Fair Transaction & User Ranking System

A robust full-stack demonstration of transaction validation, concurrency protection, idempotency handling, and multi-factor ranking fairness. Built with **Express**, **Vite**, **TypeScript**, and **React**.

---

## 🚀 How to Run the Project

1. **Install Dependencies**
   ```bash
   npm install
   ```

2. **Start the Development Server (Express API + Vite Dev Middleware)**
   ```bash
   npm run dev
   ```
   *The server starts on `http://localhost:3000` which also serves the React frontend via Vite middleware.*

3. **Build and Run for Production**
   ```bash
   npm run build
   ```
   This compiles the frontend assets to `/dist` and bundles the TypeScript Express server into a standalone CJS file `dist/server.cjs` via `esbuild`.
   ```bash
   npm run start
   ```

## 🛠️ API Documentation

### 1. `POST /api/transaction`
Processes a financial transaction (Credit or Debit) for a user with full idempotency checks and safety locks.

*   **Body Parameters:**
    *   `userId` (string, required) - ID of the target user.
    *   `type` (string, required) - Either `"CREDIT"` or `"DEBIT"`.
    *   `amount` (number, required) - Greater than `0`.
    *   `idempotencyKey` (string, required) - Unique UUID/string identifier for the request to prevent double-processing.
    *   `simulateDelay` (number, optional) - Ms to artificially delay operation to test concurrency limits.
    *   `disableLocking` (boolean, optional) - Intentionally disable mutex locking to inspect race condition errors (e.g. double-spending).
*   **Responses:**
    *   `200 OK`: Successful transaction. Returns `message`, `transaction` object, `previousBalance`, `newBalance`, and `cached: false`.
    *   `200 OK (Cache HIT)`: Identical idempotency key recognized. Returns the original response payload instantly with `cached: true` and header `X-Cache-Lookup: HIT`.
    *   `400 Bad Request`: Missing or invalid input parameters.
    *   `404 Not Found`: User does not exist.
    *   `409 Conflict`: Lock timeout due to a concurrent request already processing for the same user.
    *   `422 Unprocessable Entity`: Insufficient user funds for a `"DEBIT"` transaction.

### 2. `GET /api/summary/:userId`
Fetch a detailed activity report, metrics, and transaction history for a single user.
*   **Path Parameter:** `userId` (string)
*   **Response (200 OK):**
    ```json
    {
      "user": { "id": "user_1", "name": "Alice Vance", "balance": 450.00, "createdAt": 1782393282000 },
      "metrics": {
        "totalTransactions": 2,
        "successfulCount": 2,
        "failedCount": 0,
        "totalCreditVolume": 150.00,
        "totalDebitVolume": 50.00
      },
      "history": [...]
    }
    ```

### 3. `GET /api/ranking`
Fetch the global user leaderboard calculated with a multi-factor formula and spam countermeasures.
*   **Response (200 OK):**
    *   `rankings`: Sorted list of users with their calculated scores, transaction count, total volume, average transaction size, and active penalty states.
    *   `formula`: Description of the grading score weights and anti-abuse triggers.

## 🥇 How Ranking is Calculated

To ensure rankings represent real, healthy, and organic activity (rather than rewarding gamified or automated activity), we use a **multi-factor score system** combined with an **anti-abuse velocity limit**:

### The Scoring Formula
$$\text{Base Score} = (\text{Total Volume} \times 0.5) + (\text{Average Transaction Value} \times 0.3) + (\text{Successful Count} \times 2.0)$$

1.  **Total Transaction Volume ($50\%$ weight)**: Celebrates the absolute economic volume generated by the user.
2.  **Average Transaction Size ($30\%$ weight)**: Encourages meaningful high-value transactions instead of spam.
3.  **Transaction Count (Fixed weight of $2.0$ points per successful item)**: Rewards user retention and frequent interaction.

### 🛡️ Anti-Abuse Penalty / Manipulation Prevention
To prevent malicious players from cheating the leaderboard (e.g. scripts submitting hundreds of $0.01 debit transactions within seconds to artificially boost transaction count and game the formula):
*   **Velocity Monitor**: The system measures transaction velocity for each user inside a rolling **60-second window**.
*   **Spam Penalty**: If a user exceeds **4 transactions per minute**, they are flagged for high velocity.
*   **The Penalty Multiplier**: Flagged users are hit with a **60% penalty deduction** (score multiplied by `0.4`), forcing them down the rankings. This is updated dynamically and visible transparent on the leaderboard.

## 🔐 How Duplicate Requests and Concurrency are Prevented

### 1. Idempotency Key Engine (Duplicate Prevention)
*   Every `POST /api/transaction` request requires an `idempotencyKey` parameter.
*   The server maintains a fast key-value store mapping `idempotencyKey` to the historical status code and response payload.
*   Upon receipt of a transaction, the server performs a lookup. If a key is present, it skips the execution phase and immediately returns the cached response with a customized header `X-Cache-Lookup: HIT`.
*   This ensures that networks failures, double-clicks, or retry logic in clients **never** trigger dual deductions or credits.

### 2. Per-User Mutex Locks (Concurrency Protection)
In Node.js, while the event loop prevents thread-level parallel hazards, **asynchronous operations (I/O, database delay) can introduce severe interleaving vulnerabilities**.
*   **The Vulnerability**: If two debit requests for $100 arrive for a user with $120 balance, both will check the balance at the same time. If both checks pass before either performs the subtraction, both transactions will succeed, plunging the user into a negative balance (-$80) - a **Double Spend Attack**.
*   **The Solution**: We implemented an elegant **per-userId Mutex Lock queue**.
*   When a request arrives, it attempts to acquire a lock for the specific user.
*   If another request holds the lock, the new request pauses and waits (or times out after 4 seconds with a `409 Conflict`).
*   Once the lock is acquired, the balance check, delay, balance update, and logging are completed in complete isolation before the lock is released. This guarantees state consistency under extreme concurrent pressure.

## 📈 Technical Implementation Details & Trade-offs

1.  **In-Memory Store**: State is stored in standard memory structures (`Map` and Arrays) for high performance and clean conceptual isolation. In a distributed multi-instance deployment, this would be backed by **Redis** (for locks and idempotency caches) and a relational database like **PostgreSQL** (to guarantee atomic ACID updates).
2.  **Optimistic vs. Pessimistic Locking**: We chose pessimistic locks (`acquireLock`/`releaseLock`) for simplicity and reliability. In environments with exceptionally high write volumes, optimistic concurrency control (checking schema version/timestamp at write time) could be used to reduce lock overhead.
